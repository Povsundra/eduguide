# 10 Database Design

# 1. Purpose

## 1.1 Overview

The Database Layer provides persistent storage for all data used by the EduGuide platform.

Unlike traditional information systems that rely on a single relational database, EduGuide employs a multi-database architecture to support knowledge representation, semantic retrieval, conversational interactions, and system management.

Each storage technology is selected according to its strengths and assigned a specific responsibility within the overall architecture.

This design enables efficient graph traversal, semantic similarity search, structured data management, and scalable knowledge expansion.

---

## 1.2 Role in System Architecture

The Database Layer serves as the persistent storage foundation of the platform.

```text
                Markdown Repository
                        │
                        ▼
                 Knowledge Parser
                        │
         ┌──────────────┴──────────────┐
         ▼                             ▼
  Neo4j Knowledge Graph          Chunk Generator
         │                             │
         ▼                             ▼
 Graph Relationships          Embedding Generator
         │                             │
         └──────────────┬──────────────┘
                        ▼
                  Vector Database
                        │
                        ▼
                 AI Service Layer
                        │
                        ▼
                  PostgreSQL Database
```

Each storage component performs a specialized function without overlapping responsibilities.

---

# 2. Design Objectives

The Database Layer is designed to achieve the following objectives.

## Knowledge Representation

Store educational knowledge using graph structures that naturally represent relationships among universities, programs, scholarships, careers, and curricula.

---

## Efficient Retrieval

Support low-latency retrieval for both structured graph queries and semantic similarity search.

---

## Data Consistency

Maintain synchronization between the knowledge repository, graph database, and vector database.

---

## Scalability

Allow new educational entities and relationships to be added without redesigning the database schema.

---

## Reliability

Provide secure, consistent, and recoverable persistent storage.

---

# 3. Storage Architecture

EduGuide employs four storage layers.

| Storage | Purpose |
|----------|---------|
| Markdown Repository | Source of truth |
| Neo4j Graph Database | Knowledge representation |
| Vector Database | Semantic retrieval |
| PostgreSQL | Operational system data |

Each storage layer has a distinct responsibility.

---

# 4. Database Technologies

## Markdown Repository

Stores manually curated educational knowledge.

Examples include:

- university profiles;
- program descriptions;
- scholarship information;
- curriculum documents;
- career information.

Markdown files are the authoritative source of educational knowledge.

---

## Neo4j Graph Database

Neo4j stores structured educational knowledge as nodes and relationships.

It supports:

- graph traversal;
- recommendation reasoning;
- relationship discovery;
- entity linking.

---

## Vector Database

The Vector Database stores semantic embeddings of educational documents.

It supports:

- semantic search;
- contextual retrieval;
- similarity matching;
- Hybrid Graph RAG.

---

## PostgreSQL

PostgreSQL stores operational data generated by the platform.

Examples include:

- user accounts;
- conversations;
- recommendation history;
- feedback;
- system logs.

Educational knowledge is not stored in PostgreSQL.

---

# 8. Graph Relationship Design

Relationships describe how educational entities are connected.

Examples include:

```text
(:University)-[:OFFERS]->(:Program)

(:Program)-[:HAS_CURRICULUM]->(:Curriculum)

(:Program)-[:LEADS_TO]->(:Career)

(:Program)-[:REQUIRES]->(:AdmissionRequirement)

(:Scholarship)-[:AVAILABLE_AT]->(:University)

(:Scholarship)-[:SUPPORTS]->(:Program)

(:University)-[:LOCATED_IN]->(:Province)

(:Faculty)-[:BELONGS_TO]->(:University)

(:Faculty)-[:OFFERS]->(:Program)
```

The graph structure enables efficient traversal and relationship reasoning.

---

# 9. Vector Database Design

The Vector Database stores semantic embeddings for Hybrid Graph RAG.

Each chunk contains:

| Attribute | Description |
|-----------|-------------|
| Chunk ID | Unique identifier |
| Entity ID | Related graph entity |
| Entity Type | University, Program, Scholarship, etc. |
| Text | Chunk content |
| Embedding | Dense vector representation |
| Metadata | Filtering information |
| Source | Markdown document |
| Language | Khmer or English |

The Vector Database enables semantic similarity search.

# 11. Indexing Strategy

Efficient indexing improves query performance.

Neo4j indexes include:

- University(name)
- Program(name)
- Scholarship(name)
- Career(name)

Vector Database indexes include:

- HNSW Approximate Nearest Neighbor Index
- Cosine Similarity

PostgreSQL indexes include:

- Primary Keys
- Foreign Keys
- B-Tree indexes
- GIN indexes for full-text search

---

# 12. Database Constraints

The system enforces integrity constraints.

Examples include:

- University IDs are unique.
- Program IDs are unique.
- Scholarship IDs are unique.
- Duplicate graph nodes are prohibited.
- Required relationships must exist before recommendation.

These constraints preserve data consistency.

---

# 13. Data Synchronization

Educational knowledge remains synchronized across storage layers.

Synchronization workflow

```text
Markdown Updated

↓

Knowledge Parser

↓

Update Neo4j

↓

Regenerate Chunks

↓

Regenerate Embeddings

↓

Update Vector Database
```

This process ensures that the Knowledge Graph and Vector Database remain consistent with the source documents.

---

# 14. Backup and Recovery

The platform implements multiple backup strategies.

| Storage | Backup Strategy |
|----------|-----------------|
| Markdown Repository | Git Version Control |
| Neo4j | Database Dump |
| PostgreSQL | Scheduled SQL Backup |
| Vector Database | Rebuild from Markdown Repository |

The Markdown Repository serves as the ultimate source of truth.

---

The Database Layer supports future expansion.

The graph schema allows new node types and relationships without requiring significant structural modifications.

# 18. Summary

The Database Layer adopts a multi-database architecture to support the diverse storage requirements of the EduGuide platform.

Markdown serves as the authoritative knowledge source, Neo4j manages structured educational relationships, the Vector Database enables semantic retrieval for Hybrid Graph RAG, and PostgreSQL stores operational application data.

By separating storage responsibilities across specialized databases, the platform achieves efficient knowledge representation, scalable retrieval, reliable system operation, and maintainable long-term growth.
